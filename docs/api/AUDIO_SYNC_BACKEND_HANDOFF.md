# 백엔드 전달용 Audio 동기 연동 권장안

상태: **AI 권장 설계, 구현 전, 백엔드 검토 전**. 2026-10-04 작성.
사용자가 결정한 사항은 AI 선설계와 동기 처리이며 아래 구체 규칙은 AI 측 제안이다.
현재 CLI·DB 저장 기능이 아래 HTTP 계약을 이미 구현한 것은 아니다.

## 1. 권장 방식과 이유

백엔드가 원본 파일을 보관한 뒤 AI 내부 API에 `multipart/form-data`로 파일을 직접 전달한다.
AI는 요청 안에서 전처리·임베딩·저장 또는 검색을 완료하고 응답한다.
공유 디스크 경로나 저장소 URL 접근 규칙을 먼저 구축하지 않아도 연동할 수 있고,
AI가 요청받은 임의 경로·URL을 읽는 문제를 줄일 수 있어 초기 연동 방식으로 제안한다.
서버 간 파일 전송 비용은 발생한다. 대용량·대규모 운영 시 저장소 참조 방식은 별도 검토한다.

음악 ID는 백엔드의 Sample ID를 문자열로 그대로 사용한다. AI가 별도 음악 ID를 만들지 않는다.
아티스트 정보·권한 검사는 백엔드 책임이며 AI에는 개인정보를 복제하지 않는다.
원본 SHA-256은 동일 파일 확인용이고 음악 ID를 대체하지 않는다.

## 2. 등록·수정 계약

**`PUT /internal/v1/audio-embeddings/{music_id}`**

하나의 ID에 등록과 파일 교체를 같은 계약으로 처리한다. 제목 수정에는 호출하지 않는다.

| 입력 | 타입 | 규칙 |
| --- | --- | --- |
| music_id (경로) | 문자열 | 앞뒤 공백 없는 1~200자, 백엔드 Sample ID와 일치 |
| file | 바이너리 | 원본 음악 파일, AI가 임시 파일로 수신 |
| source_version | 정수 | 1 이상, 파일 교체·삭제 시 백엔드가 증가시킴 |
| source_sha256 | 문자열 | 소문자 16진수 64자, 백엔드 계산값과 AI 실제 파일 해시 일치 |

최초 등록은 201, 더 최신 파일로 교체는 200, 동일 버전·동일 원본 재요청은 200을 제안한다.
응답은 DB 커밋 이후 반환한다.

```json
{
  "music_id": "123",
  "source_version": 1,
  "source_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "status": "ready",
  "changed": true,
  "dimension": 1024,
  "model_version": "2023"
}
```

`dimension`은 실제 생성 결과를 반환하며 클라이언트가 고정 차원을 보내도록 요구하지 않는다.
`changed=false`는 동일 요청의 결과를 재사용한 경우다. 반환 모델·전처리 정보의 세부 필드는 구현 시 확정한다.

## 3. 파일 버전과 동시 요청 정합성

백엔드가 음악별 버전을 발급한다. 같은 음악의 버전은 재사용하거나 감소시키지 않는다.
숫자가 더 크면 최신 요청이며 삭제도 버전을 증가시키는 변경이다.

| 요청과 현재 버전 비교 | 처리 |
| --- | --- |
| 더 작음 | 409 `stale_source_version` |
| 같음·원본 해시 같음·정상 저장됨 | 결과 재사용, 200 |
| 같음·해시 다름 또는 삭제됨 | 409 `source_version_conflict` |
| 더 큼 | 새 생성 결과를 버전 검사 후 원자적으로 반영 |

생성 전 검사만으로는 동시 수정·삭제를 막을 수 없다. 생성은 DB 트랜잭션 밖에서 수행하고,
저장 직전에 현재 버전·삭제 상태를 잠금 아래 다시 확인한 뒤 벡터와 버전을 함께 커밋한다.
같은 버전의 정상 저장 재요청은 새 임베딩 생성을 생략할 수 있도록 설계한다.
새 파일 생성에 실패하면 기존 벡터를 자동으로 새 버전으로 바꾸지 않는다.

백엔드 파일 보관/교체와 AI 저장은 하나의 트랜잭션이 아니다.
백엔드는 새 파일을 처리 중 상태로 두고 성공 응답 후 새 버전을 활성화하도록 제안한다.
실패 시 기존 활성 파일을 유지하고, 새 파일을 이미 활성화했다면 검색 결과에서 이전 버전을 제외해야 한다.
이는 백엔드 화면·상태 처리의 추가 구현이 필요한 규칙이다.

## 4. 삭제와 상태 확인

**`DELETE /internal/v1/audio-embeddings/{music_id}?source_version=2`**

삭제 버전과 삭제 기록은 유지하고 벡터를 제거한다. 삭제한 행의 ID·버전 기록까지 지우면
늦게 끝난 과거 등록 요청이 음악을 다시 만들 수 있기 때문이다.
같은 삭제 버전 재요청은 성공으로 처리하고, 더 오래된 버전은 409로 거부한다.
벡터가 아직 없는 ID도 삭제 기록을 남겨 처리 중인 이전 요청을 차단한다.
삭제 커밋 후 204를 반환한다. 삭제한 ID를 서비스에서 재사용하지 않는 것을 권장한다.

**`GET /internal/v1/audio-embeddings/{music_id}`**

저장된 버전·해시·상태(`ready` 또는 `deleted`)만 반환하며 벡터·로컬 파일 경로는 반환하지 않는다.
처음부터 없던 ID는 404다. HTTP 시간 초과 후 백엔드가 결과 반영 여부를 확인하는 용도다.
현재 구현에 이러한 버전·삭제 기록·상태 조회 기능은 없다.

## 5. 음악 검색

**`POST /internal/v1/audio-search`**, `multipart/form-data`

| 입력 | 규칙 |
| --- | --- |
| file | 행사 관계자가 올린 검색 기준 음악 |
| source_sha256 | 원본 해시, AI가 실제 입력과 비교 |
| top_k | 정수 1~100, 기본 5 |
| search_request_id | 선택적인 백엔드 요청 추적 ID. 후보 음악 ID와 별개 |

검색 입력은 후보로 저장하지 않는다. 기존 공통 생성기를 사용하고 저장 후보 벡터를 비교한다.
생성 조건이 호환되고 삭제되지 않은 후보만 포함하며 동일 원본 해시는 제외한다.

200 응답 예시:

```json
{
  "search_request_id": "search-456",
  "status": "ok",
  "candidate_count": 6,
  "results": [
    {
      "music_id": "123",
      "source_version": 1,
      "rank": 1,
      "cosine_similarity": 0.64270633,
      "audio_similarity_score": 64.270633
    }
  ]
}
```

예시는 한 결과만 표시했다. 부족한 후보는 있는 만큼 반환하고 후보가 없으면
200과 `status=no_candidates`, 빈 results를 반환한다.
결과 버전도 반환해야 백엔드가 현재 활성 파일 버전과 일치하는지 확인할 수 있다.
백엔드 필터 후 결과가 5곡보다 적어질 수 있으며 재검색·충원 정책은 후속 합의한다.
현재 검색은 곡 단위이며 아티스트 Top5가 아니다. 표시 점수는 임시 유사도 지표다.

## 6. 오류·파일·접근 규칙

| HTTP | reason 예시 | 백엔드 처리 |
| --- | --- | --- |
| 401/403 | 인증·접근 거부 | 인증 설정 확인, 사용자에게 내부 정보 노출하지 않음 |
| 413 | audio_too_large | 입력 용량 수정 |
| 422 | invalid_audio / source_hash_mismatch | 원본 또는 요청 수정 |
| 409 | stale_source_version / source_version_conflict | 최신 버전 확인, 무조건 재시도하지 않음 |
| 503 | temporarily_unavailable | 제한된 재시도, 저장 상태 먼저 확인 |
| 500 | internal_error | 서버 로그 확인, 비밀 정보·스택은 응답 제외 |

오류 응답은 `{"reason":"source_hash_mismatch"}` 형태로 제안한다.
예상치 못한 DB·모델 장애를 전부 입력 오류로 바꾸지 않는다.
파일 크기·길이 상한과 타임아웃 값은 실제 처리시간을 측정해 확정한다. 측정 전 고정 성능을 약속하지 않는다.
파일명·확장자만 신뢰하지 않고 실제 디코딩 가능 여부를 확인한다.
AI는 수신 파일을 관리되는 임시 경로에 저장하고 성공·실패 후 정리한다.
백엔드 원본 파일은 시간 초과 후 결과 확인·허용된 재시도까지 보관한다.
AI 내부 API는 사용자에게 직접 공개하지 않고 서버 간 인증을 적용한다.
초기 인증은 전용 서비스 토큰과 HTTPS/사설망으로 제안하되 운영 환경과 비밀값 공급 방식은 검토한다.

## 7. 구현 순서와 백엔드 전달 사항

1. 버전·삭제 기록을 위한 추가 마이그레이션과 저장/갱신/삭제/조회 서비스 구현
2. 파일 수신·해시 검사·정리·인증을 포함한 동기 HTTP API 연결
3. 동시 갱신·삭제·중복 재요청·롤백·검색 버전 반환 테스트
4. 실제 파일로 등록→상태 확인→검색→교체→삭제 실행 검증
5. 백엔드에 요청 예시·오류·버전 관리 및 활성 파일 전환 규칙 전달

백엔드 확인 항목은 Sample ID의 문자열 전달, 파일별 버전 발급,
원본 해시 계산, 처리 중/활성 파일 관리, multipart 호출, 시간 초과 후 상태 조회다.
음악 Sample ID에는 행사 Request ID를 붙이지 않는다.
Text 저장·번역, 최종 종합 점수와 BPM/리듬은 이 계약의 범위에 포함하지 않는다.

기존 마이그레이션의 체크섬을 유지하기 위해 `0001_audio_embeddings.sql`은 수정하지 않는다.
기존 CLI 데이터의 초기 버전 부여와 전환 규칙은 추가 마이그레이션에서 명시하고,
전환 후 기존 CLI가 버전 검증을 우회하지 않도록 함께 변경해야 한다.

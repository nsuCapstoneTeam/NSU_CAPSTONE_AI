# CLAP 유사도 기반 곡 추천과 사용자 신뢰 확보 제안

작성일: 2026-10-05

> 과거 회의 제안 이력. 아래 체크리스트·역할 분담은 당시 제안이며 현행 개발 작업이 아니다.
> 2026-10-07 사용자 결정은 [AI 작업 기준](../api/CLAP_RECOMMENDATION_DIRECTION.md)에 반영했다.
> 점수·누락·오류 정책은 [Linear 서버 협의](https://linear.app/nsu-capstone/document/000-server-agreements-목록-7e0bf3793fd3)의 Accepted 문서를 확인한다.
> 당시 청취·피드백·설명 대안과 미정 항목은 기록 가치가 있어 보존한다.

상태: 회의용 Proposed. 팀 전체 합의 및 기능 구현 완료를 의미하지 않습니다.
기존 요구사항·Accepted ADR을 대체하지 않으며 회의 합의 후 변경 이력을 반영합니다.

## 1. 제안 요약

초기 추천은 관계자가 올린 기준 음악과 후보 곡의 CLAP 음악 유사도만으로 정렬하는 방식을 제안합니다.
BPM·리듬 항목 평균에 의한 종합 점수는 초기 범위에서 보류합니다.
사용자의 신뢰는 근거 없는 세부 점수보다 직접 청취, 점수 의미 안내, 확인된 행사 조건,
아티스트 정보와 실제 추천 품질 검증으로 확보하고자 합니다.

## 2. BPM·리듬을 초기 순위에서 보류하는 이유

현재 CLAP은 음악 임베딩과 유사도를 제공하지만 독립적인 BPM 수치·리듬 일치율을 직접 반환하지 않습니다.
BPM·리듬 비교 자체가 불가능한 것은 아닙니다. librosa 등의 별도 분석으로 특징을 추출할 수 있으나
현재 프로젝트에서는 추출·비교·점수화가 구현·검증되지 않았습니다.

한 곡의 구간별 템포 변화, 절반·두 배 BPM 해석, 리듬 특징과 비교 구간의 정의도 필요합니다.
검증 전 임의의 0~100 점수를 만들어 평균에 넣으면 추천 근거를 설명하기 어렵습니다.
추후 별도 분석을 추가했을 때 청취 평가와 추천 품질이 개선되는지 확인한 뒤 도입을 결정합니다.

## 3. 제안하는 처리 흐름과 책임

1. Spring이 일정·지역·예산·필수 공연 형태 등 서비스 조건으로 후보를 필터링합니다.
2. Spring이 현재 ACTIVE인 곡 ID·audioRevision 후보 쌍과 기준 음악을 AI에 전달합니다.
3. AI는 저장·검색의 공통 임베딩 생성 방식으로 기준 음악을 처리하고 저장 후보 벡터와 비교합니다.
4. AI가 CLAP 코사인 유사도 순으로 곡과 원본 유사도·표시 점수를 반환합니다.
5. Spring은 곡·아티스트 정보, 확인된 조건과 신뢰 정보를 연결해 화면에 전달합니다.
6. 사용자는 기준곡과 추천곡을 듣고 적합성을 판단하며 피드백을 남길 수 있습니다.

이 제안에서는 Spring이 의미·BPM·리듬 평균이나 별도 종합 순위를 다시 계산하지 않습니다.
Spring의 후보 필터·권한 확인·반환 revision 재검증·결과 연결 책임은 유지합니다.
AI 반환 개수, 상위 비율, 최소 점수, Top10 유지 여부, 더 보기 방식은 이번 문서에서 확정하지 않습니다.
특히 상위 10~20% 또는 점수 차이 10~20점은 실험 가능한 후보 기준이지 확정 정책이 아닙니다.

## 4. 사용자 신뢰를 위한 대처 방안

### 우선 제공할 기능

- **기준곡·추천곡 청취 비교:** 재생 대상을 명확히 표시하고 두 곡을 쉽게 전환하도록 합니다.
  분석 구간과 실제 청취 구간을 확인할 수 있도록 하고 제공 권한·접근 정책은 Backend에서 관리합니다.
- **점수 의미 안내:** '음악 유사도'로 표시하며 행사 성공 확률·일치율·신뢰성 점수로 표현하지 않습니다.
  현재 0~100 표시 변환은 임시 기준이며 사용자용 수식·정밀도는 검증 후 결정합니다.
- **확인된 행사 조건:** Backend에서 실제 확인한 일정·지역·예산 등의 통과 결과만 표시합니다.
  음악 유사도와 조건 충족을 별개 정보로 제공합니다.
- **아티스트 정보 연결:** 곡명·아티스트 프로필과 확인된 인증·활동 정보를 연결합니다.
  신뢰 데이터가 없으면 근거 부족 상태를 표시하고 높은 신뢰성을 추정하지 않습니다.

### 추천 이유의 정확성 확보

- **확실한 이유부터 제공:** 기준 음악과의 유사도 및 실제 통과한 조건을 근거로 안내합니다.
  유사도만으로 특정 악기·장르·리듬이 선정 원인이라고 단정하지 않습니다.
- **세부 음악 설명은 별도 검증:** 텍스트 비교·태깅·오디오 설명 모델은 후보 방법입니다.
  고정 문장 목록이 모든 음악을 설명할 수 있다고 가정하지 않으며 생성 설명의 사실성을 검증합니다.
- **설명 실패 시 결과 유지:** 점수와 검색 결과는 유지하고 근거 없는 문장을 대신 생성하지 않습니다.
  설명 생략·기본 문구·timeout 정책은 Backend와 합의합니다.

### 실제 품질과 운영 신뢰 확보

- **사용자 피드백:** 곡별 '비슷함/다름' 평가를 수집합니다. 자동 재학습이나 순위 반영은 별도 정책입니다.
- **별도 청취 평가:** 기존 개발 표본 외 음악에서 추천 상위 곡을 여러 사람이 평가하고
  장르·보컬·음원 길이 등 조건별 실패 사례와 평가 일치 정도를 기록합니다.
- **일관된 분석:** 모델·전처리 버전과 분석 구간을 기록하고 같은 요청의 재현성을 확인합니다.
- **장애와 결과 없음 구분:** 검색 실패를 '조건에 맞는 곡 없음'으로 표시하지 않으며,
  응답 시간·timeout·재시도는 실제 측정 결과로 결정합니다.

## 5. 현재 구현과 제안 기능의 구분

현재 구현: CLAP 임베딩, 원본 코사인 유사도·임시 표시 점수, 파일/DB 검색 CLI, Health API.

후속 구현·검증: 후보 revision 쌍 HTTP 검색 계약, 사용자 비교 화면, 추천 이유 생성,
피드백 수집, BPM·리듬 분석, 대량 후보·동시 요청 성능 검증.
이 문서에서 실행한 새로운 분석 실험은 없습니다.

- [ ] 비교 청취·조건 표시·피드백 기능의 우선순위
